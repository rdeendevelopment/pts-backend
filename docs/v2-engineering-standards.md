# PTS API v2 — Engineering Standards

Permanent rule for all work under `src/v2/`.

**Write code that a senior engineer would be happy to maintain:** simple, clear, useful, and easy for a new teammate to understand.

Legacy code under `src/app/` is out of scope. Do not import from it.

---

## 1. Folder standards

Every business module lives under `src/v2/modules/<name>/` and follows the same shape:

```text
src/v2/modules/<module-name>/
├── index.js                 # exports routes (+ public services/middleware if needed)
├── <module-name>.routes.js  # main Express router at module root
├── controllers/             # HTTP in/out only
├── services/                # business rules and orchestration
├── repositories/            # database queries only
├── models/                  # Mongoose models (*.model.js) + index helpers
├── schemas/                 # request/validation schemas (not Mongoose)
├── validators/              # express-validator rules + validateRequest
├── dto/                     # response mappers
├── helpers/                 # module-specific helpers only
├── constants/               # module constants (*.constants.js)
├── errors/                  # module error codes
├── middleware/              # module HTTP middleware (when needed, e.g. auth)
└── tests/                   # node:test files
```

Shared infrastructure stays in `src/v2/kernel/`.

**Rules:**

- One concern per file. If a file grows past ~200 lines, split it.
- Do not create `utils/helpers/misc` dumps unless the helper is used in 3+ places.
- Name folders in plain English (`auth`, `projects`, not `authenticationManagerModule`).
- Mongoose models live in `models/` — never in `schemas/`.
- Route entry file stays at module root: `<module-name>.routes.js`.
- Large modules may add `routes/` sub-files later, but the root route file remains the entry.
- New modules mount in `src/v2/index.js` inside the `env.v2.enabled` block.

---

## 2. Code style standards

1. **Simple over clever.** Prefer readable flow over patterns for their own sake.
2. **No robotic naming.** Use names a teammate would say out loud: `issueSession`, not `performAuthenticationSessionMaterialization`.
3. **No unnecessary abstractions.** No base classes, factories, or generic handlers unless repetition is real and painful.
4. **Consistent module structure.** Copy the `auth`, `modules`, or `example` layout; do not invent a new layout per module.
5. **Clear method names.** Functions should read like sentences: `assertAccountCanAuthenticate`, `revokeFamily`.
6. **Avoid copy-paste.** Extract when the same block appears twice with the same meaning.
7. **ObjectId only.** Public IDs are 24-char hex strings. No `legacyId`, no numeric IDs.
8. **Use kernel helpers.** Responses, errors, logging, and validation go through `src/v2/kernel/`.

---

## 3. Commenting standards

| Do comment | Do not comment |
|------------|----------------|
| Business rules (why a decision exists) | Obvious code (`// increment counter`) |
| Security-sensitive behavior | Restating the line below |
| Non-obvious edge cases | Large blocks of dead or speculative code |
| Placeholders tied to a future module | “Generated by …” style noise |

**Examples of good comments:**

```javascript
// A revoked refresh token used again usually means theft — revoke the whole family.
// Public registration is dev-only unless PTS_V2_ALLOW_PUBLIC_REGISTER=true.
// Placeholders until Module 3 wires real permissions.
```

Keep comments short. One or two lines is enough.

## 4. Layer responsibilities

### Controllers

- Parse request, call one service method, send response.
- No business rules, no database access, no branching beyond HTTP concerns.
- Always wrapped with `asyncHandler`.

### Services

- Own business logic and orchestration.
- Call repositories and other module services.
- Throw `AppError` with a clear `code` and useful `details`.
- Add a brief comment when a rule is not obvious from the code.

### Repositories

- MongoDB queries and writes only.
- No HTTP, no JWT, no permission checks.
- Return documents or plain data; let services decide what to expose.

### Validators

- Readable rules that QA and backend devs can review without reading service code.
- One array export per use case (`registerRules`, `loginRules`).
- Human `withMessage()` strings — not cryptic codes.
- May import shared field rules from `schemas/` when useful.

### Models

- Mongoose schemas and collection wiring only (`*.model.js`).
- Index helpers such as `ensureXIndexes()` may live alongside the model or in `models/index.js`.
- Collection names stay unchanged (`pts_accounts`, `pts_modules`, …).

### Schemas (request)

- Request body / query validation shapes — not Mongoose models.
- Example: `createProject.schema.js`, `updateProject.schema.js`.

### DTOs

- Map internal models to API-safe shapes.
- Never expose secrets (`passwordHash`, raw tokens in logs, etc.).

## 5. Error and response standards

### Success

```json
{
  "success": true,
  "data": {},
  "meta": { "requestId": "...", "timestamp": "..." }
}
```

Use `sendSuccess(res, data)` from the kernel.

### Error

```json
{
  "success": false,
  "error": {
    "code": "AUTH_INVALID_CREDENTIALS",
    "message": "Invalid email or password",
    "details": {}
  },
  "meta": { "requestId": "...", "timestamp": "..." }
}
```

Use `AppError` + `sendError` via the error handler.

**Error code rules:**

- Uppercase snake case: `DOMAIN_WHAT_HAPPENED`.
- Message should help a human debugging at 2am.
- `details` should carry structured context (`status`, `field`, `hint`) — not stack traces in production.
- Reuse module error code files (`auth/errors/authErrorCodes.js`).

## 6. Testing expectations

- Add tests for non-trivial logic: validation helpers, token/password behavior, business rules.
- Use Node’s built-in test runner (`node --test`); run via `npm run test:v2`.
- Name tests after behavior: `hashToken is deterministic`, not `test1`.
- Integration tests can come later; unit tests for services are expected when logic grows.

---

## 7. QA and debugging expectations

QA and support should be able to:

1. Read a validator file and know what the API accepts.
2. Read an error `code` and understand what went wrong without opening MongoDB.
3. Use `requestId` from `meta` to find logs.
4. Hit `/api/v2/health` to confirm v2 is enabled and Mongo is up.

When adding features, document:

- New env vars (in `docs/v2-folder-structure.md` or module doc).
- New error codes (in module error file + short note in module doc).
- curl examples for happy path and one failure path.

---

## 8. What we deliberately avoid

- Redis, queues, workers, CQRS, event sourcing (unless explicitly approved later).
- Microservices split — v2 is a **modular monolith**.
- Importing from `src/app/**` (enforced by ESLint).
- Touching legacy routes or Angular from v2 work.
- Large refactors of working modules without a clear reason.
- Importing or using `socket.io` directly from v2 business modules — all realtime emissions go through `src/v2/modules/socket` public service or module-specific socket event helpers.

---

## Realtime / socket rule

v2 modules must **not** import or use `socket.io` directly.

**Forbidden in v2 modules:**

- `io.emit(...)`, `socket.emit(...)`, `req.io.emit(...)`, `global.io.emit(...)`
- `app.get('io')`
- Hard-coded room strings (`account:…`, `project:…`, etc.) in business services

**Allowed:**

- `socketService.emitToUser / emitToAccount / emitToProject / emitToTask / emitToConversation / broadcast`
- Module event helpers that wrap the global service, e.g. `taskSocketEvents.helper.js`

Only `src/v2/modules/socket/` owns Socket.IO lifecycle, auth, and room naming helpers.

---

## 9. Review checklist (before opening a PR)

- [ ] Module follows standard folder layout
- [ ] Controllers are thin; logic is in services
- [ ] Errors use `AppError` with debuggable codes
- [ ] Validators are readable by non-authors
- [ ] No secrets in responses or logs
- [ ] Complex logic has a short “why” comment
- [ ] Tests added or updated where behavior changed
- [ ] Docs updated for new routes, env vars, or error codes
- [ ] Realtime uses global socket service or module socket event helpers (no raw `socket.io`)
